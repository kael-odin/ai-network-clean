# 静态 IP 供应商:白名单 / 封禁问题

> 结论先说:客户端这边已经能把「经你的订阅节点 → 你的静态 IP → AI 网站」这条链搭起来并跑通握手;
> 现在失败的原因在**供应商侧**:它按来源 IP 做白名单/封禁,不认识的 IP 直接拒。

## 1. 实测到的四种回复

| 我们发的 | 供应商回复 | 含义 |
|---|---|---|
| 不带认证 | `ip forbidden, userip=<来源IP>, info=ip not in allowIpList` | 这个来源 IP 不在允许列表里 |
| 带认证,来源是家宽 IP | `ip forbidden, ip banned access, ip=198.51.100.23` | 来源 IP 被**封禁** |
| 带认证,来源是订阅的美国节点 | `ip forbidden, ip banned access, ip=203.0.113.21` / `.21.22` | 机房 IP 同样被封禁 |
| 带认证,来源是香港/日本/新加坡/台湾/韩国节点 | `connect to proxy error` | 这些节点根本连不到 `5388`(多半被供应商的网络策略挡了) |
| 带**错误密码** | `user forbidden, user=demo-user, info=account password authentication failed` | 用户名认得,密码不对 |

两条重要推论:

1. **密码是对的**。带正确密码时错误从「认证失败」变成了「IP 被封/不在白名单」,说明认证过了,卡在 IP 上。
2. **`ip banned access` 是封禁,不是「没权限」**。很可能是我们做协议探测时反复用错密码 + 反复 `GET /`,
   触发了供应商的防爆破,把当时用过的 IP(家宽 + 美国节点)临时拉黑。这类封禁通常 10–30 分钟自动解除,也可能要工单解。

## 2. 三种可行配置(按推荐顺序)

### A. 供应商面板:把认证方式改成「账号密码」,关掉 IP 白名单
多数面板有「认证方式 / 授权 IP」两项。选「账号密码」且允许任意 IP,我们填好账号密码就能直连。

### B. 供应商面板:把你要用的**出口 IP** 加进白名单
- 直接连(不经节点):填你家宽的固定公网 IP
- 经节点连:填**你固定使用的那个节点**的出口 IP(节点 IP 会变,所以要选固定 IP 的节点/专线)

### C. 用「经节点连接静态 IP」,并让供应商放行节点器的网段
在客户端「设置 → 我的静态 IP」打开 **经节点连接静态 IP**,并把节点 IP 报给供应商加白。
这是大陆用户唯一现实的用法:静态 IP 本身不让大陆直连。

## 3. 客户端怎么配

| 字段 | 直连 | 经节点 |
|---|---|---|
| 类型 | `http` 或 `socks5`(这条是 **HTTP**) | 同左 |
| 地址 / 端口 | `203.0.113.10` / `5388` | 同左 |
| 账号 / 密码 | 服务商给的 | 同左 |
| 期望出口 IP | 服务商标注的出口 IP(填了才做出比对) | 同左 |
| 经节点连接静态 IP | **关** | **开**(需要先加订阅) |

填完连上后看首页:

- 「静态 IP 出口」= 正常 → 出口 IP 和期望一致
- 「静态 IP 可用」失败时会写明原因(超时/拒绝/认证/前置节点),来自内核日志解析

## 4. 自己复现供应商的回复

本仓库带了三个探测脚本(都不经过客户端,直接打供应商):

```bash
# 1) 协议探测:确认 5388 是 HTTP 还是 SOCKS5(会返回 403 的 errorMsg)
node tools/probe-proxy2.mjs 203.0.113.10 5388 <user> <pass>

# 2) 经本机内核(→你的节点)连到代理,在隧道里发带认证的请求
#    需要客户端已连接,混合端口默认 17897
node tools/probe-chain2.mjs 17897 203.0.113.10 5388 <user> <pass>

# 3) 批量换节点扫:看哪个节点的出口 IP 被允许
node tools/sweep.mjs 9333 203.0.113.10 5388 <user> <pass>
```

⚠️ 别连续试错密码:会触发防爆破,把来源 IP 拉黑(我们就踩了这个坑)。确认一次就够。

## 5. 如果供应商不给白名单

那这条静态 IP 只在「供应商认可的来源」下可用。此时的选择:
1. 换一家支持账号密码认证的静态 ISP
2. 让供应商把你要用的固定节点 IP 加白
3. 不用静态 IP,只在客户端里配订阅(AI 会走节点;出口不再固定,防封能力下降——这也是官方产品卖「独享 IP」的原因)

## 6. 应用内自检(推荐先用它)

「设置 → 我的静态 IP」下面有 **自检这条线路**:客户端会依次做四件事,并把供应商的原始回复显示出来:

1. **端口连通** — 直连不到就是网络/地域问题;经节点连不到就是节点到不了这个端口
2. **协议** — 端口讲 HTTP 还是 SOCKS5(填错类型就连不上)
3. **账号密码** — 供应商说 `authentication failed` 才是密码错;说 `ip banned / allowIpList` 是**来源 IP** 的问题
4. **建连测试** — 真发一次 `CONNECT`,过了才算这条线路能用

> 重要:确认密码只试一次。反复试错会触发供应商防爆破,把来源 IP 拉黑——本次排查就踩了这个坑,
> 结果三家供应商对家用宽带和多个节点 IP 全部返回 `ip banned access`,随后变成静默丢弃。

## 7. 本次实测结论(2026-10-31)

- 三条静态 IP 都是 **HTTP 代理**(5388 端口对 SOCKS5 问候回 `HTTP/1.1 403`)
- 客户端链路是通的:经订阅节点 `CONNECT` 到供应商返回过 `HTTP/1.1 200`,并拿到过供应商的明确回复:
  `user forbidden, user=<用户名>, info=account password authentication failed`(密码错时)
  和 `ip forbidden, ip banned access, ip=<来源IP>`(IP 被拦时)
- 之后所有来源(家宽 `198.51.100.23`、美国/加拿大/英国/德国/澳大利亚节点)都变成**静默丢弃**,
  判断是防爆破/风控升级,需要供应商侧解封或加白

## 8. 纠正:它是 SOCKS5,不是 HTTP(2026-10-31 深夜)

用户拿 Adspower 的配置截图给我看:**代理类型 = Socks5**,账号密码与给我们的完全一致,连接测试成功。
回头验证才发现:

- 我一开始向 `5388` 发 SOCKS5 问候,收到的是 `HTTP/1.1 403 ... ip forbidden`。
  **那不是协议错误,是供应商边缘 WAF 对"不被允许的来源"返回的拒绝页**——它用 HTTP 错误页代替 TCP 重置。
- 于是我把结论误判成"这是 HTTP 代理",后续所有测试都用 HTTP 去打一个 SOCKS5 端口,自然一直失败。
- 用正确协议一次就通了:

```
问候回复: ver=5 method=0x2(用户名密码)
认证: 成功
CONNECT www.gstatic.com:443: 成功 ✅
```

完整链路验收(客户端里):

```
出口 IP 203.0.113.10 = 期望出口     ← AI 网站看到的确实是静态 IP
AI 闸门:done                      ← 四项防护通过后放行
分流:Claude/ChatGPT/Gemini 实际=ip;国外=node;国内=direct
```

## 9. 它为什么"经 Clash 的 TUN 也能用"

本机当时 Clash Verge 的 TUN 是开着的,`Meta` 网卡占着默认路由。所以:

- 客户端里勾的"直连",实际上是**被 Clash 的 TUN 接管后再出去的**——这正是"经节点到静态 IP"的等价路径
- **出口仍然是 203.0.113.10**:静态 IP 是终点,中转是 Clash 的节点还是我们订阅的节点,只影响"能不能到",不影响"AI 网站看到谁"
- 这也解释了为什么"随便什么节点都能用":身份由静态 IP 决定,不由中转决定

所以两种拓扑都成立:

| 拓扑 | 配置 | 说明 |
|---|---|---|
| A. Clash TUN 提供中转 | 静态 IP 填 SOCKS5,**不勾**"经节点连接" | 最简单;但要接受"直连"其实是经 Clash 出去的 |
| B. 客户端自带中转 | 静态 IP 填 SOCKS5,**勾**"经节点连接"+ 自己的订阅 | 不依赖 Clash;需要有一个能到这台代理的节点 |

## 10. 教训

- 探测协议时,**别把 WAF 的错误页当成协议响应**:先看端口对"正确的握手"回什么,而不是对任意字节回什么
- 一次假设只发一次探测;反复试错会触发防爆破,把可用来源拉黑
- 判断"是谁的问题"要分清:TCP 通但零响应 = 网络层丢弃;`errorMsg: authentication failed` = 密码;
  `allowIpList / banned` = 来源 IP;`connect to proxy error` = 中转节点到不了

## 11. 最终结论(2026-10-31 深夜,Clash TUN 开着)

在**同一台机器、同一时刻**做了三组单次验证:

| 来源 | 结果 |
|---|---|
| 家宽直连(Clash TUN 关) | `HTTP 403 ip forbidden`(WAF 拒绝页) |
| 经我们订阅的美国节点 `203.0.113.21`(已加白) | SOCKS5 问候无响应;HTTP 探测回 `ip banned access, ip=203.0.113.21` |
| 客户端「直连」(Clash TUN 开) | ✅ 握手/认证/CONNECT 全通,出口 `203.0.113.10` |

**结论(最终版,两次独立验证):**
1. 面板的"IP 白名单"加白**不能解除已有的封禁**,`banned` 与 `not in allowIpList` 是两回事。
2. 供应商维护的是一份**具体 IP 的黑名单**,不是"封掉所有机房 IP":
   - `198.51.100.23`(家宽)、`203.0.113.21`(美国A01)→ 被拦
   - **`203.0.113.31`(日本节点A)→ 可用**
3. 所以中转节点要**挑一个不在黑名单里的**:203.0.113.x 这一段的日本节点实测可用。
4. 两种拓扑都跑通了:
   - **A(有 Clash TUN)**:静态 IP 不勾「经节点」,中转交给 Clash —— 已验证
   - **B(没有 Clash)**:勾「经节点」并固定一个能通的节点(日本节点A)—— 已验证
   两种情况下 AI 网站看到的都是 `203.0.113.10`,身份完全一致。

## 12. 两种支持的拓扑

| 拓扑 | 条件 | 配置 |
|---|---|---|
| **A. 外部 TUN 中转(本机当前可用)** | 机器上 Clash Verge 开着 TUN | 静态 IP 填 SOCKS5,「经节点连接」**不勾**;客户端会自动退回本地代理模式并复用系统 TUN |
| B. 客户端自带中转 | 本机没有别的 TUN,且你的某个节点能到这台代理 | 勾「经节点连接静态 IP」,并固定一个能通的节点 |

拓扑 A 的关键认识:**AI 网站看到的永远是静态 IP(203.0.113.10),中转是谁不影响身份一致性**;
中转只影响"能不能到达"。所以只要机器上有 Clash 之类的 TUN 在跑,这套组合就是稳定的。

## 13. Cloudflare 一直挑战的真因（2026-11-01）

用户反馈「一连上软件，打开 Claude 就一直跳 CF 验证」。内核日志给出了原因：

```
challenges.cloudflare.com:443          → AI 放行[静态 IP（美国）]
brunhild.challenges.cloudflare.com:443 → Match[普通代理（日本节点A）]
```

CF 的挑战页会从 `challenges.cloudflare.com` 的**子域名**（如 `brunhild.`）加载脚本。
模板里的规则是 `DOMAIN,challenges.cloudflare.com`（精确匹配），**子域名漏过去落到了 MATCH → 节点**，
于是挑战请求从一个 IP 发出、校验回另一个 IP —— Cloudflare 判定不一致，无限挑战。

修复：把这条规则改成**后缀匹配**并固定到静态 IP（且**不经 AI 闸门**，保证挑战资源永远能加载）：

```
DOMAIN-SUFFIX,challenges.cloudflare.com,AI 专用出口
```

验证（修复后）：

```
brunhild.challenges.cloudflare.com:443 → match DomainSuffix(...) using AI 专用出口[ 静态 IP ]
走普通代理的 challenges.* 记录数：0
```

**另一条独立的限制**：内置的 Electron 窗口即使伪装成 Chrome UA，Cloudflare 仍会对 Electron
做持续挑战（Electron 的 `navigator.userAgentData`、插件列表等与真 Chrome 有差异）。
所以「Claude」页给了两个入口：内置窗口（全链路、但可能卡挑战）与「用默认浏览器」
（走你的 Chrome/Adspower，经系统代理 → 内核，指纹是真实浏览器的，CF 通常直接放行）。
